4inOne: Was trägt, was fehlt, was zuerst

Geprüft wurden die vier Hauptbereiche und ihr Zusammenspiel – am Quellcode, mit einer automatischen Prüfung aller Demo-Seiten und einem vollständigen Durchlauf als Erstnutzerin gegen das echte Backend. Jede Aussage trägt ihre Belegart.

Bestandsaufnahme: was tatsächlich da ist

Aus Datenmodellen (backend/*/models.py), Komponenten und dem Erstnutzer-Durchlauf. Alles in dieser Liste ist Im Code bestätigt.

Finanzen

  • „Noch verfügbar“ mit Tagessatz
  • Monatsbudget mit Zeitraum
  • Kategorie-Limits, Jahreskarte

  • Fixkosten, wiederkehrend

Haushalt

  • Geräte: Garantie, Wartung, Anhänge
  • Verträge: Kosten, Frist, Verlängerung, Erinnerung

Organisation

  • Heute mit Tageslinie und freier Zeit
  • Kalender Tag/Woche/Monat
  • Geteilte Kalender mit Rollen
  • ICS-Import (einmalig, ohne Abgleich)
  • Aufgaben mit Projekt, Wiederholung, Priorität
  • Haushaltsaufgaben eingeblendet (eine Quelle)
  • Notizen mit Anheften, Schnellnotiz, Anhängen
  • Startseite: Heute aus Organisation + Haushalt

Reisen

  • Bordkarte mit Countdown und Stand
  • Fünf Reiter inkl. Budget
  • Ablauf mit Programmpunkten → Kalender
  • Planung mit Zuständigkeit
  • Packliste mit Kategorien
  • Regelbasierte Vorlagen (Art, Wetter, Transport)
  • Mehrere Währungen, „Wer schuldet wem“
  • Mitreisende mit Rollen

Querschnitt: Connection Engine mit sieben automatischen Verbindungen (Vertrag → geplante Kosten, Kündigungs-, Wartungs- und Sparziel-Erinnerung im Kalender, Haushaltsaufgaben in Organisation, Reisezeitraum und Tagesablauf im Kalender) plus manuelle und vorgeschlagene Verknüpfungen. Datenexport (DSGVO), Zwei-Faktor, Google/Apple-Anmeldung.

Nicht vorhanden Im Code bestätigt: Erinnerungen per E-Mail oder Push (Mails nur für Anmeldung und Einladungen, die Glocke kennt nur Einladungen) · Suche (layout/app-shell.ts › searchEnabled = false) · Kalenderabgleich · lernende Kategorien · Offline-Betrieb (nur Manifest, kein Service Worker) · Dunkelmodus · Packliste aus früherer Reise · Verbindung Reiseausgaben ↔ Finanzen.

Finanzen

7 / 10

Die Übersicht beantwortet die wichtigste Frage – wie viel ist noch da? – mit einer großen Zahl und einem Tagessatz. Geplante Ausgaben und Sparbeiträge sind im Code sauber von Buchungen getrennt und werden erklärt. Die Schwäche liegt in der Menge der Begriffe und in der Handarbeit: Jede Ausgabe wird von vorn getippt.

Stärken

  • „Noch verfügbar“ berücksichtigt geplante Ausgaben und Sparbeiträge, nie doppelt gezählt (recurring_planned). Code
  • Fachbegriffe mit (i)-Erklärung an Ort und Stelle (shared/ui/term-hint). Code
  • Neues Konto ohne Nullen-Wüste: Startleitfaden statt leerer Kennzahlen. Code
  • CSV-Import entfernt IBAN-Spalten, bevor etwas gespeichert wird. Code

Schwächen

  • Viele parallele Begriffe: Monatsbudget, Kategorie-Limit, geplant, Fixkosten, wiederkehrend, Sparbeitrag. Risiko
  • Kein Vorschlag aus früheren Buchungen; der Import übernimmt nur eine vorhandene Kategoriespalte. Code
  • „Kommt jeden Monat wieder“ wirkt nur bei Ausgaben; bei Einnahmen ist es nur eine Markierung. Code
  • Zeitraum-Umschalter (Tag/Woche/Monat/Benutzerdefiniert) über dem Inhalt erhöht die Komplexität der Übersicht. Risiko
  • Eingefrorene Haushaltsfinanzen (Account, Budget, RecurringDeduction, ADR-001) leben weiter im Code. Code

Erstnutzer verstehen die Übersicht schnell, stolpern aber über die Begriffsvielfalt im Budget-Reiter Nutzertest. Langzeitnutzer ermüden an der manuellen Erfassung – das ist der wahrscheinlichste Abbruchgrund in diesem Bereich Risiko.

Haushalt

7 / 10

Haushalt ist im Alltag der durchdachteste Bereich: Räume, Aufwand, Reihum und die Verteilung „wer macht wie viel“ machen ihn für Paare und WGs stark; der Einkauf merkt sich Artikel und schlägt sie vor. Die Kehrseite ist Dichte: Der Aufgabendialog bietet sieben Planungsangaben, und Verträge erinnern nur innerhalb der App.

Stärken

  • Eine Datenquelle für Haushaltsaufgaben – Organisation blendet sie ein, statt sie zu kopieren. Code
  • Einkauf abschließen erzeugt eine Ausgabe in Finanzen (ShoppingTrip.transaction). Code
  • Verträge mit Kündigungsfrist, Verlängerung, Preisänderung und Erinnerung im Kalender. Code
  • Optionale Angaben im Aufgabendialog sind gruppiert („Planung und weitere Angaben“). Code

Schwächen

  • Aufgaben, die noch nicht fällig sind, lassen sich nicht abhaken („noch nicht abhakbar“). Wer früher putzt, kann es nicht eintragen. Code Nutzertest
  • Routinen sind eine eigene Ansicht innerhalb von Aufgaben – zwei Orte für „wiederkehrend“. Risiko
  • Zuhause startet leer; typische Verträge (Strom, Internet, Handy, Versicherung) müssen von Grund auf angelegt werden. Code
  • Kündigungsfristen erinnern nur im Kalender der App – wer die App nicht öffnet, verpasst die Frist. Code

Gemeinsame Nutzung ohne Überladung gelingt bereits gut: Personen-Avatare und Reihum erscheinen erst, wenn jemand eingeladen ist (Satz „Nur du – noch niemand sonst im Haushalt“) Code. Haushalt ↔ Organisation: Beide zeigen dieselbe Aufgabe; Haushalt ordnet nach Raum und Person, Organisation nach Tag. Das ist der richtige Weg und sollte so bleiben.

Organisation

6 / 10

Organisation soll der Grund sein, 4inOne täglich zu öffnen. Die Bausteine sind gut: Tageslinie mit freier Zeit, Aufgaben nach Tag oder Projekt, Schnellnotiz, geteilte Kalender mit Rollen. Aber zwei Dinge verhindern tägliche Nutzung: Niemand erinnert an den Termin, und der echte Kalender bleibt woanders. Der ICS-Import ist einmalig – danach laufen zwei Kalender auseinander.

Stärken

  • „Heute“ zeigt Termine in Folge und die Zeit dazwischen; Haushaltsaufgaben sind eingebunden. Code
  • ICS-Import verändert unbekannte Wiederholungsregeln nicht stillschweigend. Code
  • Notizen: anheften, Schnellnotiz ohne Dialog, Aufzählung per „-“. Code

Schwächen

  • Keine Erinnerung vor Terminen oder fälligen Aufgaben außerhalb der App (keine Mail, kein Push). Code
  • Kein Kalenderabgleich; Import nur einmalig. Code
  • Keine Suche über Termine, Aufgaben, Notizen. Code
  • Drei „Heute“: Startseite, Haushalt › Heute, Organisation › Heute – unklar, welches der tägliche Einstieg ist. Risiko

Reisen

8 / 10

Reisen ist der reifste Bereich. Die Bordkarte beantwortet „wie weit bin ich?“ mit Countdown, offenen Aufgaben, Packstand und Restbudget. Vorlagen nach Reiseart, Wetter und Transport sparen echte Arbeit, „Wer schuldet wem“ löst ein reales Problem. Was fehlt: Wiederverwendung und die Brücke zu Finanzen.

Stärken

  • Vorbereitungsstand auf einen Blick (Bordkarte: Aufgaben, gepackt, übrig). Code
  • Vorschläge sind auswählbar, nichts wird ungefragt übernommen; Begründung ehrlich ohne „KI“. Code
  • Mehrere Währungen mit Kurs zum Ausgabetag; Abrechnung zwischen Mitreisenden. Code
  • 4inOne schlägt passende Sparziele zur Verknüpfung vor. Code

Schwächen

  • Keine Packliste aus einer früheren Reise übernehmen – jede Reise beginnt mit Vorlagen von vorn. Code
  • Reiseausgaben stehen bewusst neben Finanzen; das Monatsbudget kennt die Reise nicht. Code
  • „Dringend“ wird nicht hervorgehoben – vier offene Aufgaben wirken gleich, auch wenn eine morgen fällig ist. Risiko
  • Fünf Reiter pro Reise sind am Handy knapp. Nutzertest

Mobile Bedienung

Automatisch geprüft wurden alle Demo-Seiten und Reiter bei 390 px und 1440 px: keine Verstöße gegen WCAG 2.2 AA (axe), kein Querscrollen, keine Konsolenfehler Code. Untere Navigation mit fünf Zielen, Formulare als Blatt von unten, Tippflächen ≥ 44 px, runder Haken überall links.

Gut am Handy

  • Klare Hauptaktion je Bereich als Knopf unten; bei Leitfäden ausgeblendet, um nichts zu verdecken.
  • Wischbare Filterzeilen mit sichtbarem Hinweis am Rand (Kalender).
  • Anmeldung als Sheet mit Kopf in Deep Forest statt weißer Fläche.

Zu prüfen

  • Lange Seiten (Startseite, Finanzen-Übersicht) – wichtig steht oben, Rest erst nach viel Scrollen. Risiko
  • Der schwebende Knopf liegt beim Scrollen über Listenenden; Listen brauchen genug Abstand unten. Risiko
  • Lange Dialoge (Aufgabe, Vertrag) brauchen viel Scrollen bis „Speichern“. Nutzertest
  • Kein Offline-Betrieb: im Supermarkt ohne Netz ist die Einkaufsliste leer. Code

Connection Engine: Sie bleibt im Hintergrund und erklärt sich in einem Satz („Verbinden heißt: 4inOne zeigt es dort an …“). Das ist richtig so – sie sollte kein eigener Bereich werden. Ausbaustufe mit größtem Nutzen: Reise ↔ Finanzen (R3), weil dort heute doppelt gerechnet wird.

Langfristige Nutzung

Täglichschwach gestützt

Termine, Aufgaben, Schnellerfassung. Ohne Erinnerung und Kalenderabgleich fehlt der Anlass, die App zu öffnen.

Wöchentlichgut gestützt

Haushaltsplanung, Einkauf mit Gedächtnis, Verteilung. Stärkster Wiederkehr-Grund heute.

Monatlichteilweise

Budget und Sparziele klar; Rückblick vorhanden. Erfassungsaufwand bremst.

Gelegentlichgut gestützt

Reisen mit Vorlagen, Abrechnung, Bordkarte – überzeugend, aber selten.

Warum Nutzer nach einigen Wochen aufhören könnten

  • Vergessen: Nichts holt sie zurück – keine Mail, kein Push. Code
  • Doppelte Kalender: Termine müssen zusätzlich zum gewohnten Kalender gepflegt werden. Code
  • Tipp-Müdigkeit in Finanzen: jede Ausgabe von vorn, kein Lernen. Code
  • Wachsende Datenmenge ohne Suche: nach Monaten ist das Wiederfinden mühsam. Code
  • Unklare Freigaben: Familien zögern, wenn nicht sichtbar ist, wer was sieht. Nutzertest

Empfohlene Umsetzungsreihenfolge

  1. Nutzertest vorbereiten und parallel laufen lassen

    Fünf Personen ohne Technikbezug: Erstnutzung (30 Min.) und ein Termin nach zwei Wochen. Klärt die mit „Nutzertest“ markierten Punkte, bevor groß gebaut wird.

  2. Schnelle Klarheit ohne API (1–2 Wochen)

    F1 Erfassung lernt, R1 dringend, F2 Einnahmen-Option, F4 Budgetbegriffe, H2 Zuhause-Vorlagen, O2/R4 ein „Heute“.

  3. Vertrauen im Umgang (1–2 Wochen)

    Ü1 Rückgängig, H1 vorzeitig abhaken (nach Klärung der Backend-Regel), F3 Übersicht entlasten.

  4. Rückkehr-Anlass schaffen – mit deiner Freigabe

    O1 E-Mail-Zusammenfassung und Fristen-Erinnerung, dann O4 Suche.

  5. Bereiche enger verbinden – mit deiner Freigabe

    R3 Reisebudget in Finanzen, R2 Packliste übernehmen, O3 Kalender-Abo.

  6. Feinschliff

    P2-Punkte: Dialoge verschlanken, Altlasten, Offline-Liste, Dunkelmodus.

Methode und Grenzen

  • Quellcode: Datenmodelle aller vier Bereiche, Komponenten, Verbindungsregeln, Startseiten-Logik (dashboard.ts, organisation/views.py › today_data).
  • Automatische Prüfung: alle Demo-Seiten und Reiter bei 390 und 1440 px – axe (WCAG 2.2 AA), Querscrollen, Konsolenfehler, Tippflächen, Seitentitel.
  • Erstnutzer-Durchlauf: 11 Schritte gegen echtes Backend mit frischer Datenbank (e2e-fullstack/erstnutzer.spec.ts), inklusive Abschottung zweier Konten.
  • Nicht geprüft: echte Nutzer, Ladezeiten unter Last, Verhalten mit großen Datenmengen, Screenreader von Hand. Bewertungen 1–10 sind Experteneinschätzungen, keine Messwerte.
  • Skizzen: nachgebaute Ansichten nach den Regeln von stageshow (ein Brennpunkt, Platzhalter statt Fülltext, Ausschnitt statt Miniatur). Sie zeigen Ideen, keine fertigen Entwürfe.
